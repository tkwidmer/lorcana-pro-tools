# Tournament tools and the Tournament History archive

Read before touching Tournament Lookup, Store Lookup, Field Breakdown, the `/results/*` pages, `api/tournament-history.ts`, `api/_lib/tournament*.ts` or `api/_lib/sideEvents.ts`. The `ravensburger-tournament-api` skill documents the upstream API; `tournament-history-sync` is the recurring import procedure.

## Tournament Lookup

`TournamentLookupPage` accepts a Ravensburger tournament URL and extracts the event ID. It uses `tournamentApi.js` for all data:
- `fetchEventDetails` → raw event + phases + rounds
- `getTournamentStructure` → resolved current round, top-cut size, rounds remaining, advancement requirements
- `fetchTournamentStandings` → paginated standings for a specific round
- `fetchAllRegistrations` → all registered players (paginated loop)
- `analyzeId` → ID safety analysis: compares player's points buffer vs cut line, counts players who could pass them if everyone wins
- `analyzeAdvancement` → status (secured/possible/eliminated) toward the next phase cutoff

Until a round has generated standings (`currentRoundId` is null) the page shows the registered roster instead of standings. That covers all of round 1: RPH posts a round's pairings and results before it generates any standings, so once a round has started (`activeRoundId`) the page also loads its matches and shows the Matches tab beside the Roster, landing on Matches. Gating matches on standings once hid every round-1 pairing of a 778-player DLC.

## ID analysis

`analyzeId()` in `tournamentApi.js`: after an ID, a player gains 1 point. It counts how many players below the cut could leapfrog them if those players all win (+3 pts), and classifies safe (≥3 point buffer), borderline (1–2) or danger (0 or outside the cut).

## Store Lookup

`StoreLookupPage` extracts every UUID from pasted store IDs/URLs and fetches each store via `/api/tournament?type=store`, plus its events (`storeEvents`) and unique-fan count. `storeTiers.js` models RPH's store-tier program:
- `computeTierProgress()` tracks provisional Legendary progress in the pro-rating window (`PRORATE_WINDOW`, `LEGENDARY_PRORATED_REQUIREMENTS`, plus running a Hyperia City Prerelease).
- `computeStandingTierStatus()` gives the standing tier over the trailing 4 set seasons, whose boundaries are derived from Prerelease events (`deriveSeasons()`).

Each lookup writes the extracted store IDs to the URL as `?stores=<id>,<id>` (whether IDs or store URLs were pasted), so the link is shareable; opening it pre-fills the input from that param (over the localStorage last input) and auto-runs the lookup.

The page also shows a static Welcome/Standard/Legendary reference (definitions + benefits from RPH's announcement, requirements from the `*_MAINTENANCE_REQUIREMENTS` constants).

Only `display_status === 'complete'` events count. The window dates and requirements are hardcoded from the Aug 2026 program email, so they'll need updating when RPH changes the program.

## Field Breakdown

`FieldBreakdownPage.jsx` (`/field-breakdown`, supporter-gated): paste every decklist in a room (blank line between lists), or upload carde.io's decklists PDF, and see the room by ink pair (`inkPairField()` in `lib/fieldBreakdown.js`, unit-tested: each deck's two most-played inks, counted) and each list's inks, card count and unmatched names. "Copy for Stream Overlay" copies the ink pairs as `Emerald/Steel 8` lines (`inkPairLines()`), the Stream Overlay Metagame card's input. It needs only the card database; an archetype assignment against duels.ink's profiles was tried first and removed, since the Metagame chart is by ink pair.

The PDF (the carde.io admin's "Download decklists" export, one deck per page) is read in the browser by `lib/cardePdf.js` with pdf.js (`pdfjs-dist`, legacy build, loaded on first use, because the current build needs `Math.sumPrecise` and `Promise.try`); `decklistsFromPages()` (unit-tested) turns the pages into this input, rejoining a card name that wrapped and dropping the print header/footer. `scripts/carde-field-export.js` (the Stream Overlay panel's "Export carde.io decks" bookmarklet, or pasted into the DevTools console on an event's carde.io admin page) pulls every submitted decklist with the organizer's own session (Play Hub's public API carries no decks), copies the room's ink-pair lines, and leaves the full lists in this page's input format in `cardeField.fieldText`. The textarea persists in localStorage (`lorcana_field_breakdown`).

## Tournament History Archive

The caster-facing tool for surfacing a player's history across multiple imported RPH major events, and any prior head-to-head between two players in a pairing. This is the first feature to store real domain data in Supabase rather than only auth/tier metadata.

**Import (admin-only, one-shot, re-runnable):** `AdminTournamentImportPage.jsx` (`/admin/tournament-import`, linked from `AdminPage.jsx`) posts an event URL to `POST /api/tournament-history?endpoint=import`. Its **Suggested events** card is the bulk path: `?endpoint=suggested-imports` runs `api/_lib/tournamentDiscovery.ts` — the one implementation of major-event discovery (official DLC / Challenge Championship / Last Chance Qualifier templates, the CCQ, ACQ and prize-pool name searches the `tournament-history-sync` skill documents, and side events at a DLC or Championship parent's store within three days of it with 200+ players and 5+ rounds) — and returns every discoverable event that is complete, has a round with generated standings (the events list carries each round's `standings_status`, so a store that never entered results is dropped without a per-event fetch), isn't a Ravensburger test fixture and isn't in the archive; the card shows the count and total players, labels each row by category, and **Import all** imports them one at a time. There is no sync script or cache file any more: the archive is the already-imported set. That route (`requireAdmin()` in `api/_lib/requireAdmin.ts`) fetches the event's details, final-round standings, and all completed rounds' matches directly from `RAVEN_BASE`/`HYDRA_BASE` (`api/_lib/tournamentImport.ts` — a server-side port of `tournamentApi.js`'s fetch/pagination logic, since this runs in a Vercel function rather than the browser and can't go through the client-only `/api/tournament` proxy), then upserts them via `api/_lib/tournamentHistorySupabase.ts`. Re-running the import for the same event is idempotent — it always re-derives and upserts, so importing again after more rounds complete updates standings/ranks rather than duplicating rows.

**Schema** (`supabase/migrations/008_tournament_history.sql`): `tournament_history_events`, `tournament_history_standings`, `tournament_history_matches` — zero RLS policies, service-role-only access, same pattern as `discord_favorite_players`/`duels_api_tokens`/`metafy_links`. Player identity is joined by RPH's own stable `player.id` (`rph_player_id`), the same id `TournamentLookupPage.jsx`'s cross-event favorites/team-tag localStorage already keys by — never by name, which is stored only for display/search (trigram-indexed for fuzzy search). "Made top cut" is precomputed at import time (`has_elimination AND rank <= top_cut_size`) rather than needing a separate accomplishments table. Head-to-head lookups use a generated `player_pair` column on `tournament_history_matches` for an O(1) equality lookup instead of an OR'd scan.

**Caster UI:** clicking a non-bye pairing row in `TournamentLookupPage`'s Matches tab (`MatchesTab`'s `onSelectPairing`) opens `PairingHistoryPanel.jsx` — a modal showing a head-to-head banner (prior meetings across imported majors, or "first meeting") plus each player's cross-event summary (events played, top cuts made) alongside their `PlayerMatchHistory` for the currently loaded event. The panel's cross-event data and the loaded event's `PlayerMatchHistory` are two independent data sources shown side by side — this feature does not merge with `/players/:name`'s separate scouted-game/gamelog opponent-profile system (see `docs/agents/duels-data.md`); they remain unrelated.

**Public results pages:** `/results`, `/results/events/:eventId` and `/results/players/:playerId` (catalog tool "Tournament Results", Tournament Tools) expose the same archive without a session — the first free, linkable surface on it. Reads are edge-cached (`Cache-Control: s-maxage`) instead of session-gated, since the data only changes on admin import. `src/lib/resultsArchive.js` (unit-tested) derives a player's outcome per match, the summary stats (record excludes byes; best finish ties go to the larger event; up to 10 most-faced opponents) and adapts archived bracket rows to the RPH match shape `EliminationBracket` renders. Elimination matches are picked by the phase whose `round_type` is `RANKED_SINGLE_ELIMINATION` in `raw_event_details` (Swiss phase names vary per organizer). `event_date` is derived from RPH's `start_datetime` in the event's `timezone` (`eventDateOf()` in `tournamentImport.ts`); migration `019` backfilled it (numbered after `018_day_two_and_player_card.sql`, which landed in parallel) — every earlier import had left it NULL because the code read a field RPH doesn't send. The results list hides events under `MAJOR_MIN_PLAYERS` (32) by default because the discovery sweep also imports tiny CCQ trial events. `PairingHistoryPanel`'s player cards link to the player's results page ("Full history →"). Per-event/per-player sitemap entries and prerendering are deliberately not done (prerender runs against `vite preview`, which has no `/api` functions).

**Day 2 in the archive:** `tournament_history_standings.made_day_two` (migration `018`), precomputed at import like `made_top_cut`: a player made Day 2 if they played a match in the event's second Swiss phase (a DLC's "Day Two Swiss"; matches carry `phase_name`), counted only when that phase holds fewer players than started, since a few side events run everyone through two Swiss phases. `player-history` returns `madeDayTwo` per event and `dayTwoCount`.

**Majors vs side events:** `event_tier` is the official template (`challenge`, `challenge_championship`, `lcq`, or a generic tier), and CCQs and the large side events of a DLC weekend both sit on generic templates, so `api/_lib/sideEvents.ts` (unit-tested) decides: an event at the same `store_name` as a `challenge`/`challenge_championship` event within three days of it, not on a major template itself, is a side event. A generic-tier event that isn't a side event is a major only at `MIN_MAJOR_PLAYERS` (100) starting players (`isMajor()`): the archive also holds CCQ trials, CCQ side events and third-party locals imported for their head-to-head history (the cost: the sub-100 Asian ACQs and the Asia Championship main event aren't counted). `player-history` flags each event `sideEvent` and `major` and returns `majorsPlayed` beside `eventsPlayed`; `topCutCount`/`dayTwoCount` count majors only. The Stream Overlay player card's "Majors" tile and `PairingHistoryPanel`'s "Majors played" read `majorsPlayed`; side-event finishes still show with a "Side event" tag.

**API** (`api/tournament-history.ts`, `?endpoint=` dispatch, folded into one function per the function budget in `docs/agents/api-routes.md`, which also lists each endpoint's auth): `import`, `recent-imports`, `suggested-imports` (admin-only), `recompute-ratings` (admin or `CRON_SECRET`), `pairing-badges` (any session), and the public, edge-cached reads `events`, `event`, `event-player`, `player`, `player-history`, `head-to-head`, `search-players`, `ratings`.

## Player ratings

A Glicko-1 rating per RPH player over every archived match (spec: `docs/superpowers/specs/2026-10-26-player-ratings-design.md`). Glicko-1, not Glicko-2: volatility adds nothing for players seen in a few bursts a year, and the rating deviation (RD) is what handles bursty data.

- **The model** (`api/_lib/glicko.ts`, pure, tested in `api/_lib/__tests__/glicko.test.ts` against Glickman's worked example): 1500 ± 350 for a new player. One event is one rating period: events run in `event_date` order, ties by `rph_event_id` (numeric), and every match in an event updates against the opponents' ratings as they stood at the start of the event, so round order inside it does not matter; Swiss and top cut both count. Win 1, loss 0, draw 0.5. Byes and the unreported matches (no winner, not a draw, about 3,200 of them) are **skipped, not counted as losses**. Before each of a player's periods their RD grows with days away, `sqrt(RD² + c²·days)` capped at 350, with `c ≈ 18.05` so RD 60 returns to 350 after a year. A winner who is neither player throws.
- **Thresholds:** established means RD ≤ 100 (`ESTABLISHED_RD`), about two events; only established players are ranked. A provisional player shows a rating, never a rank.
- **Storage:** `tournament_history_ratings` (migration `025`, service-role only): one row per player with rating, RD, matches, W/L/D, last event date, the latest name, and `history`, one `{ rphEventId, eventDate, rating, rd }` point per rated event. An index on `(rd, rating desc)` serves the leaderboard and the rank count.
- **Recompute:** always from scratch, since an import can add an older event that changes everything after it. `recomputeRatings()` in `tournamentHistorySupabase.ts` pages every non-bye match and every event in 1,000-row `.range()` pages (supabase-js returns at most 1,000 rows per request), runs `rateEvents()`, upserts in 1,000-row chunks, then deletes rows the run did not write. It runs nightly at 03:00 UTC (`.github/workflows/ratings-recompute.yml`, `CRON_SECRET`) and from **Recompute ratings** on `/admin/tournament-import`, which shows the player count and elapsed time; after an import, ratings are stale until one of those runs. `vercel.json` gives the route 60 s (the Hobby default is 10 s); the read is the cost, the math is milliseconds.
- **Reads:** `ratings` returns the top 100 established players with `delta`, the change since their previous rated event. `player` and `player-history` carry `rating: { rating, rd, matches, rank, established, history }`, `null` for a player with no rated match; `rank` is counted at read time (established players rated higher, plus one) and is null while provisional.
- **Surfaces:** `/results/ratings` (`ResultsRatingsPage`, linked from the Tournament Results header and the catalog), the Rating tile and rating-over-events line on `/results/players/:id`, the Rating tile on the Stream Overlay player card and a `casterPoints()` line ("Rated 1,712, ranked 14th in the archive") for an established player, and the rating in `PairingHistoryPanel`. `formatRating()` and `ratingDelta()` in `resultsArchive.js` format it everywhere on the site.
